## Questions: blocked event loop

### 1. What happened to the other events while you were stuck on the slow handler?

The other events remained in the event queue and waited. They could not be processed until the slow handler finished and the event loop became available.

### 2. What would a user see if this happened in a real application?

The application could appear frozen. The user might not be able to click buttons, move the window smoothly or see the interface update.

### 3. How could this problem be fixed?

Long-running tasks should be moved away from the Event Dispatch Thread (EDT), for example to a background thread or SwingWorker. GUI updates should still be performed on the EDT.

## Reflection

The event queue stores events that are generated by user actions, timers and other sources until they can be processed. The event loop continually checks the queue and takes events for processing. It sends each event to the appropriate listener and handler so that the application can respond. Events are normally processed one at a time on the Java Swing Event Dispatch Thread. If a handler takes too long, other events remain waiting in the queue and the interface may freeze. Long-running work should therefore be done in a background thread, while changes to Swing components should be made on the EDT. The event loop should not be blocked because the application needs to remain responsive to the user.
